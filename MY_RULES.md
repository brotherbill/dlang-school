# dlang‑school Repository Governance Doctrine

This file defines the non‑negotiable rules that govern the dlang‑school repository.  
These rules ensure:  
- deterministic workflows  
- zero drift  
- reproducible results  
- clean handoffs  
- stable onboarding  
- long‑term maintainability  

This doctrine applies to all contributors, tools, and processes.

---

# 1. Purpose of This Repo
This repo contains the architecture, lessons, specifications, and documentation for **dlang‑school**, including:

- the Rich Client App (RCA) specifications  
- lesson markdown files  
- badge definitions  
- folder layout rules  
- versioning rules  
- adventure system  
- onboarding instructions  
- parental report specifications  

This repo **does not** contain or reference:

- video production tools  
- Camtasia or Audiate pipelines  
- internal production utilities  
- student projects  

---

# 2. RCA Definition
**RCA = Rich Client App.**

The RCA is the local application used by students to:

- view lessons  
- render markdown  
- track badges  
- manage versions  
- navigate adventures  
- view reference projects  
- generate parental reports  

The RCA is:

- a companion  
- a navigator  
- a discipline enforcer  

The RCA is **not**:

- a parental control system  
- a surveillance tool  
- a video player  
- a web app  
- a brand or product name  

“RCA” is an internal architectural term only.

---

# 3. Badge System Doctrine
Badges represent **mastery**, not gamification.

A badge means:

- the student has internalized a tool  
- can use it comfortably  
- can apply it in multiple contexts  
- has muscle‑memory confidence  

Badges are **not**:

- icons  
- stickers  
- points  
- leaderboard tokens  

There is **no competition** and **no ranking**.

---

# 4. Markdown Mastery Requirement
Before using the RCA, students must be able to:

- open markdown files  
- read them  
- edit them  
- save them  
- understand formatting  

**Typora** is the recommended viewer/editor for young engineers.

Markdown is a core engineering skill.

---

# 5. DVORAK Typing Requirement
Students are encouraged to learn DVORAK touch typing using:

https://learn.dvorak.nl/

Typing is a lifetime skill and part of the onboarding process.

---

# 6. Folder Layout Rules
The folder layout must support:

- multiple projects per day  
- multiple versions per project  
- immutable locked versions  
- deterministic structure  

Structure:

```
projects/
    yyyy/
        mm/
            dd/
                project-name-v1/
                project-name-v2/
                project-name-v3/
                project-name-v4/
                ...
```

Rules:

- A project name **must not** end with `-`, `-v`, or `-v#`.  
- Only the RCA or CLI tools may create version folders.  
- Locked versions are **immutable**.  
- Students must not edit or delete locked archives.  

---

# 7. Versioning Rules
Versioning supports **unlimited attempts**.

Definitions:

- v1 = first attempt  
- v2 = second attempt  
- v3 = third attempt  
- …  
- vN = Nth attempt  

Rules:

- Students may need 1 attempt or 10 attempts.  
- Only one active version at a time.  
- Locked versions cannot be modified.  
- Version folders must be complete and self‑contained.  
- The RCA enforces version discipline.  

---

# 8. Lesson File Rules
All lessons are markdown files with:

- purpose  
- prerequisites  
- reference example  
- adventure task  
- micro‑steps  
- badges  
- reflection questions  

Lessons must be:

- short  
- clear  
- actionable  
- testable  

No lesson may depend on a video.

---

# 9. Parental Report Rules
Parental reports are:

- optional  
- generated by the RCA  
- emailed automatically  
- **positive in tone**  

Reports include:

- accomplishments  
- lessons completed  
- badges earned  
- versions created  
- adventure progress  
- time spent  

Reports do **not** include:

- frustration  
- obstacles  
- failures  
- negative language  
- punitive controls  

The RCA is **not bound** by parental controls.

---

# 10. notes/chat.md Rules
`notes/chat.md` is:

- chronological  
- append‑only  
- a historical ledger  
- never a driver of workflow  
- never a place for decisions  

It records:

- what was done  
- when it was done  
- why it was done  

It does **not** contain:

- plans  
- tasks  
- future intentions  

---

# 11. Commit Discipline
Every commit must:

- have a clear message  
- represent a complete thought  
- avoid mixing unrelated changes  
- maintain repo cleanliness  

Examples:

```
Add ARCHITECTURE.md: foundation of dlang-school system
Update MY_RULES.md: governance doctrine
Add notes/chat.md: initial ledger
```

No “misc fixes.”  
No “update.”  
No “stuff.”

---

# 12. Zero Drift Doctrine
This repo must remain:

- deterministic  
- predictable  
- stable  
- clean  

Rules:

- No undocumented changes  
- No silent edits  
- No speculative files  
- No abandoned experiments  
- No half‑finished features  

If a change is made, it must be:

- documented  
- committed  
- justified  

---

# 13. Markdown File Header Rules
Every Markdown file in this repo must begin with the following three lines:

**Line 1:** A level‑1 header (`#`) describing what this file is for  
**Line 2:** A level‑6 header (`######`) containing the full absolute path using Linux‑style forward slashes  
**Line 3:** A blank separator line

Example:

```
# Overview of the dlang‑school architecture  
###### /dev/repos/dlang-school/docs/ARCHITECTURE.md  

# Architecture
...
```

Rules:
- Line 1 must always be a Header 1 (`#`) describing the purpose of the file.  
- Line 2 must always be a Header 6 (`######`) containing the full absolute path using Linux‑style forward slashes.  
- Line 3 must always be blank.  
- No content may appear before Line 1.  
- No exceptions.
